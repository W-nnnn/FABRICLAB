# FABRICLAB 后台管理端设计说明

来源：需求规约 V1.1 后台需求 `FR-A-01~07`、验收 `AC-25~29`、实验指导书「后台商品管理 / 用户管理 / 订单管理 / 其他功能」、《实验一实施方案》T12~T17、`01-schema.sql` 数据模型。术语与字段名沿用配套 DDL，界面文案使用服装语义。

## 一、角色与职责

| 角色 | 说明 | 可进入 | 职责 |
|---|---|---|---|
| 匿名 | 未登录访问者 | 仅后台登录页 | 无 |
| `CUSTOMER` | 顾客账号（`store_user.role`） | 仅用户端 | 被管理对象：可被查看、修改显示名 / 邮箱 / 电话、重置密码、启用停用 |
| `ADMIN` | 管理员账号 | 仅后台 | 分类、商品、库存、相册、账号、订单的维护 |

- 后台不细分权限等级，`ADMIN` 为唯一后台角色；不新增角色表、不新增权限字段。
- 两端角色互斥：`ADMIN` 不得登录用户端，`CUSTOMER` 不得登录后台，两侧登录页均以统一失败提示拒绝。
- 管理员账号本身不被后台账号管理功能修改，避免自我锁死与角色越界。

### 主流程与异常（摘要）

| 用例 | 主流程 | 异常与结果 |
|---|---|---|
| UC-A1 | 输入用户名与口令 → 校验角色与启用状态 → 更换会话标识 → 写最小身份 → 跳转控制台 | 不存在 / 口令错 / 停用 / 角色不符 → 统一提示「账号或口令不正确，或无后台权限」，用户名回显、口令不回显 |
| UC-A3 | 新增一级 → 新增二级（挂父级）→ 编辑名称与排序 → 删除 | 编码重复、同级同名、父级不存在 → 400；有二级或有商品引用 → 删除被拒 400；创建后编码与父级不可改 |
| UC-A4 | 新增商品（款号、二级分类、价格、面料 / 版型 / 工艺、封面）→ 编辑 → 上下架 → 删除 | 款号重复、价格 ≤0、三级分类、分类不可用 → 400；停售走「下架」；有订单明细引用时删除被拒 |
| UC-A5 | 输入正整数增量 → 基于最新库存加算并递增 `version` | 增量非正整数、商品不存在 → 400 / 404；编辑页库存只读，改库存只能走补货入口 |
| UC-A6 | 按商品维护相册顺序与来源说明 | 无相册时回退封面，封面缺失再用缺省图，不阻断商品展示 |
| UC-A7 | 列表（仅 `CUSTOMER`）→ 修改显示名 / 邮箱 / 电话 → 重置口令 → 启停 | 用户名与角色不可改；重置后该账号既有会话下一次请求即失效；重复启停提示当前状态 |
| UC-A8 | 订单号完整精确匹配、五状态筛选、分页 → 详情读成交快照 | 订单号 >40 字符或非法状态 → 400；不存在 → 404 |
| UC-A9 | 修改收货三项（限待支付 / 待发货）→ 删除（仅已取消且无凭证） | 其余状态改单被拒；有效交易订单删除被拒，先明细后主表 |
| UC-A10 | 发货（仅 `PAID`）→ 写首次发货时间 | 待支付、已发货、已取消发货被拒；重复发货不覆盖首次时间 |

## 三、模块划分

```
fabriclab/admin/                         后台工程，端口 8081，独立会话
├── config/        MyBatis-Plus 分页、拦截器装配（CSRF、访问检查）
├── controller/    登录、控制台、分类、商品、补货与相册、账号、订单
├── security/      会话级 CSRF 令牌与服务端校验、后台访问检查
├── service/       各模块业务口径（唯一写入口，控制器不直接写库）
├── model/         表单参数与状态口径对象（白名单、长度、区间）
├── entity/        与用户端共享的同名七张表映射（仅后台用到的部分）
└── mapper/        对应 Mapper
```

边界约定：

1. 后台与用户端是两个独立 Spring Boot 工程，不通过 Maven 父工程或依赖互相引用，只共享同一个数据库实例与同一份 `01-schema.sql`。
2. 表结构、字段名、金额与库存口径必须与用户端一致；后台不新增表、不新增字段、不改 DDL。
3. 业务规则的唯一实现点在服务层：控制器只做参数接收、调用与视图选择；模板不参与校验。
4. 库存与价格改写只发生在服务层的条件更新中，且必须维护 `product.version`，与用户端下单、取消的写入路径互斥。

## 四、页面流程

```
/admin/signon  ──登录成功──▶  /admin/console  控制台
      ▲                            │
      │                     ┌──────┼───────┬────────┐
      │                     ▼      ▼       ▼        ▼
      │            分类维护  商品维护  账号管理  订单管理
      │             /admin/categories  /admin/products  /admin/users  /admin/orders
      │                     │      │       │        │
      │                  补货/相册 编辑/上下架 改信息/重置/启停 详情/改单/删除/发货
      └──未登录或角色不符──（访问检查重定向，携带站内返回地址）
```

- 列表页 GET 整页刷新，筛选、排序、页码全部落在查询串上，翻页保留条件。
- 写操作一律 POST + CSRF，成功后 `redirect` 回列表或详情（PRG，避免刷新重复提交），失败重渲表单并保留输入（口令类字段不回填）。
- 结果反馈经一次性提示呈现：成功为确认文案，失败为具体原因（如「款号已存在」），不使用弹窗脚本。
- 错误码：参数非法 400、CSRF 缺失或篡改 403、资源不存在 404、技术异常 500（通用文案，不暴露 SQL 与堆栈）。
- 后台页面不复用用户端模板与静态资源，导航、配色沿用品牌三色但版式为管理台（左侧模块导航 + 右侧内容）。

## 五、字段与状态

### 5.1 字段口径

| 表 | 可写字段 | 创建后不可变 | 由系统维护 |
|---|---|---|---|
| `category` | `code`、`parent_id`、`name`、`sort_order` | `code`、`parent_id`（层级不可迁移） | `parent_key`（数据库生成列） |
| `product` | `sku`、`category_id`、`name`、`description`、`fabric`、`weight_note`、`fit_note`、`craft_note`、`price`、`stock`、`status`、`cover_image`、`sort_order` | `sku` | `version`（每次库存或价格等改写递增）、`created_at`、`updated_at` |
| `product_image` | `product_id`、`image_path`、`sort_order`、`source_note` | — | 无 |
| `store_user` | `display_name`、`email`、`phone`、`status`、`password_hash`（重置） | `username`、`role` | `updated_at` |
| `sales_order` | 收货人、电话、地址（限状态）；`status`（仅发货） | 订单号、金额、明细、凭证、支付方式 | `shipped_at`（首次发货时间） |

- 价格 `DECIMAL` 以 `BigDecimal` 承载，界面固定两位小数与 ¥；后台改价只影响之后的订单，已下单明细为成交快照，不改写。
- 库存为整数且不小于 0；后台补货是**增量**语义，不接受绝对赋值；编辑商品表单中的库存字段只读。
- 单 SKU 口径：不设尺码、配色字段，尺码与配色写进商品名称或描述；后台表单同样不提供规格矩阵。

### 5.2 状态与合法迁移

```
商品：DRAFT（草稿，用户端不可见） ──上架──▶ ON_SALE ──下架──▶ DRAFT
订单：PENDING_PAYMENT ──支付──▶ PAID ──发货(后台)──▶ SHIPPED ──确认收货(用户)──▶ COMPLETED
      PENDING_PAYMENT ──取消(用户)──▶ CANCELLED
账号：ENABLED ⇄ DISABLED（停用后既有会话下一次受保护请求即失效）
```

- 状态迁移由服务层重查当前状态后以条件更新完成，不信任表单提交的状态值。
- 后台只新增一条迁移：`PAID → SHIPPED`；其余订单状态由用户端动作产生，后台不得写入。
- 非法迁移（如待支付发货、重复发货、已取消发货）一律拒绝并提示当前状态。

### 5.3 并发与版本

- 商品被下单、取消、补货、改价并发写同一行时，以 `version` 条件更新保证后写者失败而非覆盖。
- 后台打开的是旧表单（`version` 已过期）时，保存被拒并提示「商品已被其他操作更新，请重新加载」，不静默覆盖新库存。

## 六、权限矩阵

| 入口 / 操作 | 匿名 | `CUSTOMER` | `ADMIN` |
|---|---|---|---|
| `GET /admin/signon`、`POST /admin/signon` | 允许 | 拒绝（统一失败提示） | 允许 |
| `POST /admin/signout` | 403 / 重定向 | 重定向登录页 | 允许 |
| `GET /admin/console` | 302 → 登录页 | 302 → 登录页（并失效会话） | 允许 |
| `/admin/categories/**`、`/admin/products/**` | 302 → 登录页 | 302 → 登录页 | 允许 |
| `/admin/users/**` | 302 → 登录页 | 302 → 登录页 | 允许 |
| `/admin/orders/**` | 302 → 登录页 | 302 → 登录页 | 允许 |
| 用户端 `/main`、`/category`、`/product` | 允许 | 允许 | 用户端独立校验拒绝 |
| 用户端 `/cart`、`/orders`、`/checkout` | 302 → 用户端登录页 | 允许 | 用户端独立校验拒绝 |

- 访问检查以路径前缀 `/admin/**` 为范围，登录页例外；检查内容为「会话有身份 + 库中 `role=ADMIN` + `status=ENABLED`」，三者缺一即拒绝。
- 角色或状态在登录后被改动时，下一次请求即被拦截并使会话失效，不依赖会话内的旧身份。
- 两端会话互不承认：Cookie 名不同（`ADMINSESSION` / `STORESESSION`）、端口不同、会话属性键不同，互相携带对方 Cookie 不产生任何权限。

## 七、会话与安全

| 项 | 口径 |
|---|---|
| 端口 / 上下文 | 8081，后台路径统一 `/admin` 前缀 |
| 会话 Cookie | `ADMINSESSION`，`HttpOnly`，与用户端 `STORESESSION` 名不同 |
| 会话内容 | 仅身份（账号 ID、用户名、显示名）与登录时间、CSRF 令牌；不存业务数据 |
| 会话固定防护 | 登录成功后更换会话标识再写入身份 |
| 超时 | 30 分钟空闲失效 |
| CSRF | 会话级随机令牌，全部 POST 校验，缺失或篡改返回 403 |
| 口令 | BCrypt 存储；不回显、不写日志、不进查询串；重置为统一初始教学口令 |
| 输出 | 模板统一转义，商品文本字段按纯文本输出保留换行 |

## 八、控制台口径

- 控制台不放横幅式「经营数据」：不展示订单量、销售额、转化率、访客数等任何后台未真实统计的指标。
- 控制台只呈现三类可核对内容：当前登录管理员身份（账号、显示名、角色、本次登录时间）、后台模块范围与所属需求、会话与访问规则提示。
- 后续模块页面上的数量（列表总数、分页信息）只能来自真实查询结果，不得写死或估算。
- 无数据时展示空状态文案，不以示例数字填充。

## 九、与用户端的一致性约束

1. 同库同表：两侧读写同一 `MyPetStore` 库的七张表，后台改动在用户端下一次查询即生效（AC-25 的跨端证据）。
2. 金额：订单总额只由明细合计而来，后台不改金额；改价只作用于新订单。
3. 库存：后台补货为增量并推 `version`；用户端下单为条件扣减，两者并发以 `version` 与前缀条件保证不丢失更新（AC-28 需两个实际运行的应用验证）。
4. 停售：用「下架」表达，不删除商品；确实无引用时才允许删除，避免破坏历史订单与相册。

## 十一、T14 实现口径（库存与相册）

- 补货：`POST /admin/products/{id}/restock`。只收正整数增量（1—9999），服务端重查最新 `stock` 与 `version` 后条件更新 `stock = stock + n, version = version + 1`，影响 0 行即提示「库存刚被其他操作更新，请重新加载后再补货」。商品保存不再接收库存，编辑页库存只读。
- 相册：`/admin/products/{id}/album`，子动作 `/{imageId}`（改）、`/delete`、`/cover`。不新增表、不改 DDL：图类型（F 平铺 / W 上身 / D 细节）与来源许可编进 `product_image.alt_text`，格式 `F|来源|替代文本`，由 `AlbumText` 编解码；用户端 `AlbumCaption` 只取替代文本，历史数据按「平铺图、无来源、原文即替代文本」兼容。
- 封面与回退：设为封面写 `product.cover_image` 并推 `version`；相册为空时用户端回退封面，封面为空再用缺省图，后台在相册页写明这条回退。
- 预览图：后台相册页使用与用户端同路径的 320px 缩略图（`admin/static/images/products`），仅用于后台预览，用户端仍用原图。

## 十二、T15 实现口径（账号管理）

- 范围：`/admin/users` 列表与 `/admin/users/{id}` 详情。只读写 `role='CUSTOMER'` 的账号；管理员或不存在账号一律 404，不泄露存在性，也避免自我锁死与角色越界。
- 列表：用户名包含匹配（大小写不敏感，由库排序规则决定）、状态筛选（全部 / 已启用 / 已停用）、`ORDER BY id ASC`、页大小 10 / 20 / 50。行的订单数与累计金额按 `user_id` 聚合 `sales_order` 得到，不做估算。
- 资料：显示名（必填，≤50）、邮箱（可空，≤100，填写时须为有效地址）、电话（可空，≤30，仅数字、空格与 `+ - ( )`）。用户名与角色即使被提交也不接受变更，提交不同值即 400。
- 重置口令：写 `password_hash = BCrypt('Passw0rd!2026')`，每次换新盐；不显示新口令输入框，页面只写明统一初始口令。旧口令立即失效。
- 会话失效：用户端登录时把口令散列的指纹（SHA-256 前 16 位十六进制）写进会话 `storeCredentialTag`；`AuthInterceptor` 每次受保护请求比对库中当前散列的指纹，对不上即失效会话并跳登录页。改显示名、邮箱、电话不改散列，因此不会踢掉在线会话。
- 启停：`ENABLED ⇄ DISABLED`，带原状态条件更新；重复操作不写库，提示「该账号已是当前状态 · <当前状态>」。停用后用户端既有会话在下一请求失效，并无法再登录；历史订单与快照不变。
- 历史订单：账号页只读 `sales_order`，编辑资料不写订单任何字段，收件人以订单快照为准。

## 十三、T16 实现口径（订单管理）

- 范围：`/admin/orders` 列表与 `/admin/orders/{orderNo}` 详情。订单号是路径与查单的唯一键，超 40 字符直接 400（与 DDL 列宽一致）；不存在一律 404。
- 列表：订单号**完整精确匹配**（不接受片段）、五状态筛选（分段器带实时计数）、`ORDER BY created_at DESC, id DESC`、页大小缺省 10，可选 10 / 20 / 50。状态筛选白名单校验，非法值 400。
- 详情读快照：明细（款号、名称、单价、数量、小计）、合计金额、支付方式与凭证全部来自 `sales_order` / `sales_order_item` 成交快照，只读呈现；流转记录按下单 / 支付 / 发货 / 完成 / 取消五个节点展示，未发生节点空心。
- 修改收货信息：仅 `PENDING_PAYMENT`、`PAID` 接受；收货人必填 ≤50、电话必填 ≤30（仅数字、空格与 `+ - ( )`）、地址必填 ≤255。更新带 `status IN (待支付, 待发货)` 条件，防止并发状态变更后被改；其余状态一律拒绝。
- 发货（UC-A10）：仅 `PAID → SHIPPED`，条件更新同时写 `shipped_at`。条件更新即互斥点——待支付、已发货、已完成、已取消发货被拒并提示当前状态；重复发货命中 0 行，首次发货时间不会被覆盖（AC-29）。
- 删除（UC-A9）：仅 `CANCELLED` 且 `payment_no IS NULL` 的教学演示订单；同一事务先删 `sales_order_item` 后删 `sales_order`。其余任何状态的删除请求一律拒绝，有效交易订单不可删（AC-29）。
- 边界：金额、明细、凭证、支付方式、订单号、状态机其余迁移后台一律不写；两端同库，后台发货后用户端重新查询即为 `SHIPPED`，无同步动作。
