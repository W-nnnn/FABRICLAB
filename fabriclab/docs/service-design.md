# FABRICLAB · 客服模块设计说明

> 扩展模块（单独分支、单独 PR）｜用户端 8080 `/service`｜管理端 8081 `/admin/service`
> 与课程 `01-schema.sql` 的七张业务表并存，新增两张咨询扩展表。

## 1. 范围与定位

| 做 | 不做 |
|---|---|
| 售前选购咨询：尺码版型、面料洗护、下单与模拟支付、到店试穿 | 退款、退换、售后工单、物流轨迹、投诉赔付 |
| 会员与客服在同一会话内多轮问答 | 即时通讯、机器人自动应答、邮件/短信外发 |
| 真实库持久化、两端读同一份对话 | 伪造在线状态、虚构响应时效与满意度数字 |

依据：`MyPetStore-PRD.pdf` 3.3「本期排除」明确列出**售后工单**，7.1 要求控制台不显示「售后待办」假数据，6.12 要求订单详情移除售后入口。本模块因此定位为**选购咨询**，不改变订单状态、金额、库存，也不在任何订单页添加售后入口；控制台与铃铛里的「待回复咨询」是当次 `COUNT(*)`，不是待办假数据。

## 2. 任务归属与差异说明

- 方案「阶段 8 · 其他功能」允许扩展单独分支单独 PR、不影响 P0；本模块按同一节奏实现，不改写 AC-01~32 的既有结果。
- 与 PRD 3.3 的冲突采用兼容实现：保留「客服」这一用户要求的功能入口，同时严格不实现被排除的售后单据流程；常见问题、页脚服务区、客服中心文案都不承诺退款、退换与物流追踪。
- 课程七张表结构、字段名与约束保持原样。咨询数据存于两张**扩展表**，DDL 独立于 `01-schema.sql`，未初始化时控制台与铃铛按 0 处理、不阻塞既有页面。
- 页脚「服务」列原有静态「配送与退换」与排除项冲突，改为真实「客服中心」入口并移除该项。

## 3. 角色与权限矩阵

| 能力 | 游客 | 会员 CUSTOMER | 管理员 ADMIN |
|---|---|---|---|
| 客服中心常见问题、服务信息 | ✓ | ✓ | ✓（后台另有入口） |
| 我的咨询列表 / 详情 / 发起 / 追问 / 关闭 / 重开 | — | 仅本人 | — |
| 全站咨询列表 / 详情 / 回复 / 关闭 / 重开 | — | — | ✓ |
| 他人咨询 | — | 404，不泄露存在性 | ✓ |

用户端 `/service/threads` 与 `/service/threads/**` 由 `AuthInterceptor` 每次请求复核角色与启用状态；管理端 `/admin/**` 由 `AdminAuthInterceptor` 统一检查。全部写操作 POST + CSRF + PRG，一次性提示。

## 4. 页面与路由

**用户端**

| 路由 | 内容 |
|---|---|
| `GET /service` | 客服中心：5 组常见问题（按站点实际能力作答）、服务范围、门店与联系方式、发起与查看入口、本人待回复真实数 |
| `GET /service/threads` | 我的咨询：状态筛选（ALL/OPEN/REPLIED/CLOSED）、分页、消息数与最后一条摘要 |
| `GET /service/threads/new` | 发起咨询：类别、主题、正文、选填订单号与款号；字段级错误回填 |
| `POST /service/threads` | 新建会话与第一条消息 |
| `GET /service/threads/{id}` | 完整对话、关联信息、追问 / 关闭 / 重开 |
| `POST …/reply` `…/close` `…/reopen` | 状态迁移 |

入口：页脚服务区、账户中心导航、商品详情「就这件咨询尺码或面料」（自动带入款号）。

**管理端**

| 路由 | 内容 |
|---|---|
| `GET /admin/service` | 全站列表：四段真实计数、关键字（编号/主题/会员名/款号/订单号）、分页与页大小记忆 |
| `GET /admin/service/{id}` | 详情：会员资料、咨询信息、关联订单/款号跳转、完整对话、回复与状态动作 |
| `POST …/reply` `…/close` `…/reopen` | 回复、关闭、重开；保留筛选条件的返回链接白名单校验 |

入口：侧栏「顾客 · 客服咨询」、顶栏铃铛「待回复咨询」、控制台待办与模块范围、顶栏搜索「咨询」范围。快捷回复只把真实话术插入输入框，不自动提交、不伪装发送。

## 5. 数据模型

脚本：`store/src/main/resources/db/customer-service.sql`（可重复执行，含演示数据）。导入顺序见 `db/README.md`。

| 表 | 关键字段 | 约束 |
|---|---|---|
| `service_thread` | `thread_no`（唯一）、`user_id`、`category`、`subject`、`status`、`related_order_no`、`related_sku`、`last_activity_at`、`first_replied_at`、`closed_at` | 类别/状态 CHECK；`CLOSED ⇔ closed_at` 成组约束；`user_id → store_user` |
| `service_message` | `thread_id`、`sender`、`author_id`、`author_name`、`body`、`created_at` | 正文非空、发送方 CHECK；`thread_id → service_thread` |

`related_order_no` / `related_sku` 是展示用快照：新建时服务端复核订单号属于本人、款号真实存在，不参与订单状态、金额、库存运算。演示数据覆盖待回复、已回复、已关闭、追问后重回待回复四种状态。

## 6. 状态机

```
新建/重开 ──► OPEN 待回复 ──客服回复──► REPLIED 已回复
                  ▲                        │
                  └──── 会员追问 ──────────┘
OPEN / REPLIED ──关闭──► CLOSED ──重开──► OPEN
```

- 每次迁移用「编号 + 本人（用户端）+ 原状态」条件更新，重复提交与两端并发不会写出第二次迁移；`first_replied_at` 只写首次，`closed_at` 关闭写入、重开清空。
- `CLOSED` 不能回复或追问；重复关闭、重开非关闭会话给出「已处理」提示，不写库。
- 会员追问把 `REPLIED` 置回 `OPEN`，后台铃铛与控制台计数随即变化。

## 7. 校验与呈现

| 项 | 规则 |
|---|---|
| 主题 / 正文 / 回复 | 1—60 / 1—1000 字，去首尾空白，服务端校验 |
| 关联订单号 | 选填，≤40，须为本人完整订单号 |
| 关联款号 | 选填，≤40，`[A-Za-z0-9_-]+`，须真实存在 |
| 查询参数 | 状态白名单、页码 ≥1 归一、页大小 1—50（后台 10/20/50），超长关键字截断 |
| 输出 | 消息正文一律 `th:text` 转义，`white-space:pre-wrap` 保留换行；无脚本注入、无技术串 |
| 统计 | 列表四段计数、页头、铃铛、控制台待办全部来自当次 SQL |
| 语言 | 用户端与后台各自 `messages*.properties` 中英双语；数据库中文内容走 `tr.t` |

## 8. 验收要点

1. 游客可读 FAQ，直接访问 `/service/threads` 跳登录；缺 CSRF 的 POST 403。
2. 新建写主表 + 首条消息；非法表单保留输入并定位字段；他人订单号、不存在款号、不存在咨询均被拒。
3. 会员只能看自己的会话，越权 404；状态筛选与分页正确；非法状态 400。
4. 回复 → 已回复且首次回复时间不变；追问 → 待回复；关闭幂等；重开清空关闭时间。
5. 后台列表四段计数与关键字、分页正确；控制台与铃铛显示真实待回复数；全局搜索「咨询」直达列表。
6. 两端全量 `mvn test` 通过；浏览器实测两端提交—回复—追问闭环与数据库前后一致。
